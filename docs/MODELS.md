# Models and hardware

**The central design rule: no model is ever named in Go source.** Models are
registry entries. Hardware is a detected profile. Both are data you can edit
without recompiling, because the good local model in six months is not the good
local model today.

---

## 1. Two machines, very different maths

| | Ultrabook | Workstation laptop |
|---|---|---|
| GPU | RTX A500 Laptop — **4 GB VRAM** | RTX 4090 Laptop — **16 GB VRAM** |
| CPU | Ultra 7 155H, 16C/22T | — |
| RAM | 30 GB | 16 GB |
| 27B **Q4** (~16.5 GB) | ~95% on CPU | Near-fully offloaded |
| — est. generation | **2–4 tok/s** | ~30–40 tok/s |
| 27B **Bonsai 1-bit** (3.53 GiB) | **MEASURED: 3838/4096 MiB VRAM, loads in 5s** | Fully in VRAM @ ~100K ctx |
| — generation | **MEASURED: ~4.5 tok/s** | not yet measured |

Estimates from memory bandwidth, not measured — `froe bench` (planned, not yet built; see `docs/ROADMAP.md`) is meant to replace
them with real numbers per machine. **Quantisation class dominates everything
else**: the same 27B is a 16.5 GB CPU-bound crawl at Q4 and a 3.53 GiB
near-resident model at 1.125 bpw. Never reason about a model from its parameter
count alone. PrismML publish figures only for Apple Metal and H100 — there are
no consumer-NVIDIA numbers, so the ultrabook and the 4090 both need measuring.

**Generation speed is not the binding constraint — prefill is.** Agentic coding
is prefill-heavy: reading one 2000-line file is ~25k tokens of context. On the
ultrabook's CPU that is minutes of silence before the first token. This is why
the repo map in `docs/ARCHITECTURE.md` §5 is a core feature rather than a
nicety — on constrained hardware, *what you put in the context window* matters
more than how fast the model generates.

**The two-laptop trick.** The workstation runs `llama-server` bound to the LAN
(or Tailscale); the ultrabook points at it as a remote provider. Same binary,
same config shape, one line changed — and the big model becomes usable from the
weak machine without a single byte leaving the house. This is the highest-value
path available and needs no new code beyond a base URL.

## 2. Machine profiles

Auto-generated by `froe doctor` on first run, then yours to edit. Lives at
`~/.config/froe/machines/<hostname>.toml`.

```toml
[hardware]                       # detected, refreshed by `froe doctor`
gpu     = "NVIDIA RTX A500 Laptop"
vram_mb = 4096
ram_mb  = 30000
threads = 22

[roles]                          # which model plays which part, on THIS box
fast  = "qwen2.5-coder-1.5b"     # commit messages, classification, naming
main  = "qwen2.5-coder-7b"       # interactive editing
heavy = "remote-workstation"     # multi-file reasoning — delegated

[remote.workstation]
base_url = "http://192.168.1.42:8080/v1"
model    = "bonsai-27b"
```

Three roles, not one. Sending a commit-message request to a 27B is waste; the
1.5B already does it well and returns instantly. The router (§4) exploits this.

## 3. Model registry

`config/models.toml` ships defaults; `~/.config/froe/models.toml` overlays your
own. Adding a model that does not exist yet is an edit to a text file.

```toml
[[model]]
id            = "bonsai-27b"
runtime       = "llamacpp-prismml"   # NOT the upstream llama.cpp — see §5
params_b      = 27
quant         = "Q1_0_g128"          # 1.125 bpw binary
size_gb       = 3.53
ctx_max       = 262144
tool_strategy = "native"             # native | grammar | react
vision        = true
thinking_budget_tokens = 2048        # reasons by default; cap it
roles         = ["main", "heavy"]
comfortable_vram_mb = 6000           # 5.2 GB peak @ 4K ctx
```

`froe doctor` cross-references the registry against detected hardware and tells
you plainly which models will fly, which will crawl, and which will not load —
rather than letting you discover it during a task.

> **`bonsai-27b` — verified 2026-09-11.** A 1.125 bits-per-weight *binary*
> quantisation of Qwen3.6-27B by PrismML. Apache 2.0. GGUF at
> `prism-ml/Bonsai-27B-gguf`; LM Studio merely catalogues it, it is not
> exclusive to LM Studio. Binary GGUF is **3.53 GiB** on disk (ternary 6.66 GiB,
> vision tower +0.9 GiB); peak memory 5.2 GB at 4K context, 5.6 GB at 10K,
> 11.6 GB at 100K. 262K context, native OpenAI-style tool calling, vision,
> reasons by default with a configurable `thinking_budget_tokens`.
>
> **Measured on the ultrabook 2026-09-11** via LM Studio's plain-`Q1_0` build:
> loads in 5.02 s at 4.41 GiB, occupying 3838 of 4096 MiB VRAM — effectively
> GPU-resident. Generation is nonetheless **~4.5 tok/s**, well under the ~8–15
> estimated here from bandwidth alone, and far under the vendor's 44 tok/s on an
> M5 Pro. Residency was never the bottleneck: the RTX A500 is a 64-bit-bus part,
> and 1-bit kernels are compute-heavy rather than bandwidth-bound. **Estimating
> throughput from footprint does not work** — which is the case for `froe bench`.
>
> **It reasons by default and this is the dominant cost.** An uncapped reply to a
> four-line function request spent 504 of 567 tokens thinking: 128.7 s. Capping
> with `thinking_budget_tokens = 64` gave the same correct answer in 27.8 s —
> **4.6x faster**. `/no_think`, `chat_template_kwargs.enable_thinking` and
> `reasoning_effort` were all tested and are ALL ignored; only
> `thinking_budget_tokens` works. Any provider adapter must send it.
>
> **The PrismML fork may not be needed.** `lms get prism-ml/bonsai-27b` resolves
> to `lmstudio-community/Bonsai-27B-GGUF` — plain `Q1_0`, converted from upstream
> llama.cpp — and it runs. The fork is required only for the `Q1_0_g128` build.
>
> **It requires the PrismML llama.cpp fork** (`github.com/PrismML-Eng/llama.cpp`,
> `Q1_0_g128` hybrid-attention kernels). Upstream llama.cpp cannot load it.
> See §5.

## 4. Router

Maps task kind → role → model, per machine:

| Task | Role | Rationale |
|---|---|---|
| commit message, branch name, classify | `fast` | Small model is sufficient and instant |
| single-file edit, explain, review | `main` | Needs code competence, bounded context |
| multi-file refactor, architecture, debugging | `heavy` | Needs real reasoning; worth the latency or the hop |

Always overridable: `froe --model <id>`, or pin per-project in `FROE.md`.
Automatic routing that cannot be overridden is worse than no routing.

## 5. Runtime backends — the decision

Target the **OpenAI-compatible `/v1/chat/completions` shape** as the primary
abstraction. That single adapter covers llama.cpp, Ollama, LM Studio, vLLM,
Mistral and DeepSeek, and any future runtime following the convention.

| Runtime | Verdict |
|---|---|
| **llama.cpp (`llama-server`)** | **Recommended local backend.** Everything else wraps it. Exposes GBNF grammars (guaranteed-valid tool calls — the single biggest local reliability win), precise `--n-gpu-layers` control, KV-cache quantisation, and speculative decoding. Pairing a 27B target with the already-installed 1.5B as a draft model is a plausible 1.5–2× speedup on the workstation |
| **Ollama** | **Supported and kept working** — already installed, lowest friction, good model management. Two things to hard-code around: `num_ctx` defaults to 4096 and **silently truncates** (this reads as "the model got stupid" when it is actually your context being cut off), and no GBNF exposure, so it falls back to `native` or `react` tool calling |
| **LM Studio** | **First-class.** Bundles its own build and ships kernels ahead of upstream — it carries Bonsai-27B in-catalogue, making it the zero-effort path to models upstream cannot load. Runs **fully headless**: the `llmster` daemon needs no GUI at all (`lms daemon up`, `lms server start`), with JIT model loading and OpenAI-compatible endpoints, so it needs no new adapter. Free for commercial use since July 2025, no licence request. The one real drawback is that it is a **closed binary** — inference stays local so code never leaves the machine, but the app is not auditable, which matters given why this project exists |
| **Jan.ai** | Same: llama.cpp underneath, GUI-first, thinner ecosystem. Supported by accident, not targeted |
| **llama.cpp forks** | **A runtime is a binary path, not a name.** PrismML's fork is required for Bonsai's `Q1_0_g128` kernels and upstream cannot load that format. Froe must therefore support several llama.cpp builds side by side — each a `[runtime]` entry with its own binary, port and capability flags — rather than assuming one `llama-server` |
| **vLLM** | Server-grade, wants real VRAM. Wrong for a laptop, right if a GPU box ever appears |

```toml
# ~/.config/froe/runtimes.toml — several llama.cpp builds can coexist
[runtime.llamacpp]                  # upstream
binary   = "~/.local/bin/llama-server"
base_url = "http://localhost:8080/v1"
grammar  = true

[runtime.llamacpp-prismml]          # PrismML fork, Q1_0_g128 kernels
binary   = "~/src/prismml-llama.cpp/build/bin/llama-server"
base_url = "http://localhost:8081/v1"
grammar  = "unverified"             # open question — see below
```

**SETTLED 2026-09-11 — the fork is not required.** Upstream llama.cpp
(commit `3bcfeb7`, CPU-only build) loads `lmstudio-community/Bonsai-27B-GGUF`
(plain `Q1_0`) and serves it over `/v1`. Only PrismML'"'"'s own `Q1_0_g128` build
needs their kernels. Upstream additionally exposes `--reasoning off`, which
genuinely disables Bonsai'"'"'s reasoning where LM Studio could only cap it — 129s
versus 14.8s on the same prompt.

Build used (no CUDA toolkit on this machine, and none needed: GBNF is a sampler
feature):

```bash
git clone --depth 1 https://github.com/ggml-org/llama.cpp ~/src/llama.cpp
cmake -B build -DGGML_NATIVE=ON -DLLAMA_CURL=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build build -j 20 --target llama-server
llama-server -m <gguf> --port 8080 -c 4096 --jinja --reasoning off
```

**The CPU-only build is slow**: ~1.3 tok/s generation and roughly 4 tok/s
prefill, against ~5 tok/s generation via LM Studio'"'"'s GPU path. For speed keep
LM Studio; for control and auditability use upstream.

API vendors are the same code path plus a key: Mistral (EU-hosted, EU-governed
— the sane fallback when governance forbids US processing), DeepSeek, OpenAI.
Anthropic needs its own adapter for wire-format reasons only.

## 6. Bench harness

**Planned, not yet built** — see `docs/ROADMAP.md`. Today `eval/run.sh` measures
pass rate and time only.

`froe bench` will run a fixed task set against a model on the current machine and
record real numbers into the session DB: prefill tok/s, generation tok/s,
tool-call validity rate, task completion rate.

This is what makes "find the perfect model" tractable. Public leaderboards
measure benchmarks; this measures *your* model on *your* hardware doing *your*
work. When the next promising 20B drops, the answer to "is it actually better
for me" is one command, and the machine profile updates from evidence rather
than vibes.
